A Custom Entity: Mechanics + Decisions + Extension Points

Proposed architecture. Component implementations and helpers are supplied by the framework; event handlers define the entity's algorithm.

Entity definition copied as one versioned bundle

Components: reusable mechanics

  • Storage and capacity
  • Processing slots / resources
  • Transport track or cargo
  • Validated operations and metrics

Behavior: algorithm and state

  • Typed state and parameters
  • Arrival / start / completion
  • Transfer attempts / departure
  • Named timers and typed messages

Hooks: explicit extension points

  • Declared by the behavior
  • Called at visible code locations
  • Optional recipe or user function
  • No duplicate event algorithm
Components expose helpers; behavior uses them and calls its declared hooks

Reserve receiving space before unloading when physical unloading cannot finish without it. The transporter stays unavailable for another incompatible task.

Which existing handlers implement this?

on_messageReceive transport_task and domain responses. Queue or refuse a task using an explicit policy.
on_timerHandle named movement completions such as pickup_reached and destination_reached. They are not extra universal lifecycle stages.
on_start / completePerform loading or unloading operations. Record operation outcomes once, even when the following handoff waits.
Transfer lifecycleCheck final admission, hold cargo while blocked, and commit ownership changes once. Departure notifications belong to the source owner of each handoff.
Optional failure logicInterrupt travel/work, invalidate old deadlines and apply a declared resume or restart policy.
